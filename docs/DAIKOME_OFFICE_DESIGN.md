## 1. なぜ「入れ込む」が正しいのか

給料ソフトも売上管理ソフトも、世の中のものは **元の数字を人が手で打ちます**。
ダイコメだけは違います。**メーターが、走った実績を自動で持っている。**

```
メーター（自動で貯まる）
   └→ 売上管理 ─→ 請求書
        └→ 歩合給の計算 ─→ 給料明細
             └→ 集計（会社の数字）
```

運転代行の給料は「1件いくら」「売上の◯％」の歩合が中心です。
その元ネタをアプリ自身が持っているので、**手入力ゼロで給料まで出せます**。
競合（配車名人・精算名人など）を含めて、ここが繋がっている製品は見当たりません。
※競合の詳細は未調査。売り文句に使う前に実地で確認します（捏造しない）。

そして客は「運転代行の社長」ひとりで完結します。士業向けの Kyually とは客が別。
＝**独立させて、ダイコメの中に全部入れるのが筋が通っています。**

## 2. いちばん大事な原則：計算の中身は二重に持たない

給与計算は毎年法律が変わります（保険料率・最低賃金・所得税）。
**同じ計算を2箇所に書くと、法改正のたびに2回直すことになり、必ず片方を直し忘れて金額が狂います。**

> **決め**：給与計算は **Kyually の `lib/`（`calc.js` / `pay-rule.js` / 社保・所得税・最賃…）を唯一の正**とする。
> ダイコメはそれを **借りて呼ぶだけ**。ダイコメ用に書き直すのは禁止。

### 借り方（社内に既にある方式をそのまま使う）

`scripts/zeroact-test-commons/` が既に「1つのソースを各リポジトリへ配る」方式（git read-tree / subtree）で
運用されています。**同じやり方**で給与エンジンを配ります。

```
payslip-app/lib/  ←（唯一の正）
      │  git read-tree --prefix=lib/pay-commons
      ▼
Daikou-app/lib/pay-commons/   ← ダイコメは読むだけ・ここを直接編集しない
```

- ダイコメ側から `lib/pay-commons/` を**編集したら赤にするテスト**を置きます（うっかり分岐の防止）。
- 同じテストを両リポジトリで走らせ、**片方だけ直したらズレて赤**になるようにします。

**ダイコメが自分で持ってよいのは「実績 → 歩合の入力値」に変換する薄い層だけ**です。
（例：「この人の今月の件数は52件、売上は318,400円」を作るところまで。そこから先の税・社保は共有エンジン）

## 4. データ（表）— ★実装を読んで確定 (2026-07-31)★

**v0では表を1つ（`dk_jobs`）にしていましたが、実装を読んだら間違いでした。**
メーターは**2階建て**でデータを持っています。ここを合わせないと売上も給料も合いません。

### まず言葉を揃える（ここが一番混乱する）

| このドキュメントでの呼び方 | アプリの中身         | 何を指すか                              |
| -------------------------- | -------------------- | --------------------------------------- |
| **勤務**（シフト）         | `business` / `state` | **業務開始 → 業務終了**。1晩の勤務全体  |
| **代行**（1件）            | `trip`               | **代行開始 → 精算終了**。**課金の単位** |

司さんが「業務」と言うときは、**たいてい「代行1件」**（代行開始→精算終了）を指しています。
コードの中の `business` は「勤務全体」です。**この2つは別物**なので、以下では「勤務」「代行」と書き分けます。

### メーターが実際に持っているもの（`js/business.js` 実測）

```
勤務(business)  start_time / end_time
                total_distance_m   総走行（空車込み）
                actual_total_m     実車の合計
                fare_total_yen     売上合計
                trip_count         代行の件数
                trips[]  ────────┐
                                 │
代行(trip)  ─────────────────────┘
            distance_m / fare_yen / start_time / end_time
            start_address / end_address / waypoints[]
```

※ 空車距離 ＝ `total_distance_m − actual_total_m`（`getReport()` が計算）
※ 履歴は **localStorage に30日だけ**保持（`daikou_business_history` / `RETENTION_DAYS = 30`）
　→ **今は30日で消えます。**クラウドに上げること自体が、それだけで価値になります。

### 作る表

すでにある `dk_companies` / `dk_company_devices` に加えて。
※置き場所は当面は今の共有倉庫。リリース直前に全部まとめて新しい倉庫へ引っ越します（§10）。

| 表                                 | 中身                                                     | 備考                                      |
| ---------------------------------- | -------------------------------------------------------- | ----------------------------------------- |
| `dk_shifts`                        | **勤務1回**。開始/終了・総走行・実車合計・売上合計・件数 | 稼働時間・空車率・時給計算の元            |
| `dk_trips`                         | **代行1件**。距離・料金・時刻・出発/到着住所・経由地     | **課金と歩合の元ネタ。ここが主役**        |
| `dk_drivers`                       | ドライバー。名前・歩合の決め方・在籍                     | 端末とは別（1人が複数端末を使う日もある） |
| `dk_customers`                     | 掛け先（法人客）。請求先・締め日                         | 現金客は登録不要                          |
| `dk_invoices` / `dk_invoice_lines` | 請求書と明細                                             | 発行済みは凍結（後から金額が動かない）    |
| `dk_pay_runs` / `dk_pay_slips`     | 給与の計算単位と結果                                     | 中身の計算は共有エンジン（§2）            |

**`dk_trips` は `dk_shifts` にぶら下がります**（どの勤務の何件目か）。
歩合の「1件いくら」は `dk_trips` の件数、「売上の◯％」は `dk_trips` の `fare_yen` 合計から出します。

### 絶対に守ること

- **距離も料金も、メーターが確定した値をそのまま入れる。事務所側で再計算・補正しない。**
  （課金距離 `distance_m` は不可侵）
- **★距離の精度を語るときは必ず「代行1件ごと」。★**
  複数件の合計距離や、時間で勝手に区切った区間で精度を論じるのは**禁止**
  （課金は代行1件ごとなので、合計が合っても1件ずつズレていたら運賃が割れる）。
  集計画面に「今月の総走行距離」を実績として出すのは構いませんが、
  **それを精度や運賃の根拠には使わない**こと。
- **確定した料金は後から動かさない。**訂正は「訂正の行を足す」形にする。
- 請求書を発行したら、その明細は凍結。
- **アップロードは業務の邪魔を一切しない**（§5）。送信失敗で代行が止まることは絶対にない。

## 8. 給料の型 ＝ 飲み屋アプリと同じものを使う（2026-07-31 決定）

**新しく考える必要はありませんでした。**飲み屋売上管理アプリ（`nomiya-uriage.html`）に、
まさに必要な型が既に実装されています。

```
支給 ＝ 基本  ＋  バック  ＋  歩合     （最低保証がある人は高い方）
控除 ＝ 罰金  ＋  厚生費  ＋  前借りの返済
```

- **バック**は品目ごとに **「円」か「％」かを選べる**（`back` / `backPct`）
- **歩合**は売上に対する％（`rate`）
- **最低保証**は「計算結果」と比べて高い方を採る

運転代行にはこう当てはまります。**構造は1文字も変えず、当てはめる対象だけ差し替え**ます。

| 飲み屋                           | ダイコメ（運転代行）                                        |
| -------------------------------- | ----------------------------------------------------------- |
| 基本（時給・日給）               | 基本（時給・日給） **そのまま**                             |
| 品目ごとのバック（ボトル◯円 等） | **代行1件あたり◯円**（＋深夜・遠距離などの区分ごとに円/％） |
| 売上の歩合％                     | 売上の歩合％ **そのまま**                                   |
| 最低保証                         | 最低保証 **そのまま**                                       |
| 控除（罰金・厚生費・前借り）     | 控除 **そのまま**                                           |

これは司さんの既存方針
**「給料の項目は選べるスタイルで全アプリ統一」**（飲み屋の次の指示）とも一致します。
＝ ダイコメを作ることが、そのまま全アプリ統一を1歩進めることになります。

**★税・社保・控除の計算そのものは Kyually の共有エンジン（§2）を呼ぶ。ここは作らない。★**

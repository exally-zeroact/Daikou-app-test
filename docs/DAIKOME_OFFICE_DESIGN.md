## 1. なぜ「入れ込む」が正しいのか

給料ソフトも売上管理ソフトも、世の中のものは **元の数字を人が手で打ちます**。
ダイコメだけは違います。**メーターが、走った実績を自動で持っている。**

```
メーター（自動で貯まる）
   └→ 売上管理 ─→ 請求書
        └→ 歩合給の計算 ─→ 給料明細
             └→ 集計（会社の数字）
```

運転代行の給料は「1件いくら」「売上の◯％」の歩合が中心です。
その元ネタをアプリ自身が持っているので、**手入力ゼロで給料まで出せます**。
競合（配車名人・精算名人など）を含めて、ここが繋がっている製品は見当たりません。
※競合の詳細は未調査。売り文句に使う前に実地で確認します（捏造しない）。

そして客は「運転代行の社長」ひとりで完結します。士業向けの Kyually とは客が別。
＝**独立させて、ダイコメの中に全部入れるのが筋が通っています。**

---

## 2. いちばん大事な原則：計算の中身は二重に持たない

給与計算は毎年法律が変わります（保険料率・最低賃金・所得税）。
**同じ計算を2箇所に書くと、法改正のたびに2回直すことになり、必ず片方を直し忘れて金額が狂います。**

> **決め**：給与計算は **Kyually の `lib/`（`calc.js` / `pay-rule.js` / 社保・所得税・最賃…）を唯一の正**とする。
> ダイコメはそれを **借りて呼ぶだけ**。ダイコメ用に書き直すのは禁止。

### 借り方（社内に既にある方式をそのまま使う）

`scripts/zeroact-test-commons/` が既に「1つのソースを各リポジトリへ配る」方式（git read-tree / subtree）で
運用されています。**同じやり方**で給与エンジンを配ります。

```
payslip-app/lib/  ←（唯一の正）
      │  git read-tree --prefix=lib/pay-commons
      ▼
Daikou-app/lib/pay-commons/   ← ダイコメは読むだけ・ここを直接編集しない
```

- ダイコメ側から `lib/pay-commons/` を**編集したら赤にするテスト**を置きます（うっかり分岐の防止）。
- 同じテストを両リポジトリで走らせ、**片方だけ直したらズレて赤**になるようにします。

**ダイコメが自分で持ってよいのは「実績 → 歩合の入力値」に変換する薄い層だけ**です。
（例：「この人の今月の件数は52件、売上は318,400円」を作るところまで。そこから先の税・社保は共有エンジン）

## 3. 画面（ダイコメ事務所）

ダイコメは今 **2つの顔**を持ちます。これに3つ目を足します。

| 顔 | 誰が使う | 何を |
|---|---|---|
| メーター（`index.html`） | ドライバー | 走る・料金・オフラインで動く（**ここは触らない**） |
| 会社ダッシュボード（`dashboard.html`） | 社長 | 会社URL/QR・台数・端末管理（**実装済み**） |
| **事務所（新規）** | 社長・事務 | **売上 / 請求 / 給料 / 集計** |

事務所のタブ構成（案）：

1. **売上** … 業務1件ずつの一覧（日付・ドライバー・区間・距離・料金・支払方法）。日別/月別の締め。
2. **請求** … 掛け（月末払い）の法人客ごとに、その月の明細を集めて請求書に。
3. **給料** … ドライバーごとの歩合を実績から自動計算 → 共有エンジンで明細に。
4. **集計** … 会社の数字（売上・件数・単価・時間帯・ドライバー別）。

## 4. データ（新しい倉庫に置く表）

すでにある `dk_companies` / `dk_company_devices` に加えて：

| 表 | 中身 | 備考 |
|---|---|---|
| `dk_jobs` | **業務1件＝代行1回**。開始/終了時刻・距離・料金・値引き・支払方法・区間 | すべての元ネタ |
| `dk_drivers` | ドライバー。名前・歩合の決め方・在籍 | 端末とは別（1人が複数端末を使う日もある） |
| `dk_customers` | 掛け先（法人客）。請求先・締め日 | 現金客は登録不要 |
| `dk_invoices` / `dk_invoice_lines` | 請求書と明細 | 発行済みは凍結（後から金額が動かない） |
| `dk_pay_runs` / `dk_pay_slips` | 給与の計算単位と結果 | 中身の計算は共有エンジン |

### 絶対に守ること

- **`dk_jobs` の距離は、メーターが確定した値をそのまま入れる。事務所側で再計算・補正しない。**
  （課金距離 `distance_m` は不可侵。距離分析は業務別＝代行開始→精算終了のみ。合計や勝手な分割はしない）
- **確定した料金は後から動かさない。**訂正は「訂正の1行を足す」形にする（値引き・キャンセルは既に実装済みの考え方に合わせる）。
- 請求書を発行したら、その明細は凍結。

## 5. オフラインとの兼ね合い（ダイコメの生命線）

- **メーター側は今まで通り完全オフラインで動きます。**事務所機能はメーターに一切ぶら下がりません。
- 業務データは「繋がった時にまとめて送る」だけ。送れなくても業務は続きます。
- **業務中（客を乗せている間）は、何があってもブロックしません。**（既存の絶対ガードをそのまま踏襲）
- 事務所画面は社長・事務がネットのある所で開くもの。オフライン要件はありません。

## 6. 請求書の出し方（過去の失敗を繰り返さない）

- **Excel と PDF を「1枚の完全一致」で作るのは断念済み**（代行請求で結論が出ている）。
- よって：
  - **データは Excel（シート分け）で出す**
  - **見せる/渡す紙は「原寸表示 → 新しい窓で印刷」方式**で PDF にする
    （Kyually の Web 明細で実証済みの方法。`html2canvas`/`jsPDF` は使わない）

## 7. 今の代行請求アプリ（Exally側）はどうするか

**推奨：移植せず、この設計で作り直す。**

理由：Exally 側の請求書・給与明細は **もともと新版と総入れ替えの予定**があり、
今の実装を最終形として運びこむと二度手間になります。
引き継ぐのは「中身の考え方（テンプレート定義・内税10%・会社ごと様式）」と、上の出力方式だけ。

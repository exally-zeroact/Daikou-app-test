## 何をするのか（ひとことで）

ダイコメが今つないでいる倉庫は、Kyually や代行請求と**同じ倉庫**（Supabase プロジェクト `tnfwipbgfgjaymlszeid`）です。
これを **ダイコメ専用の新しい倉庫**に引っ越します。

引っ越すのは以下だけです（ダイコメの他の部分は元から独立しています）。

| 引っ越すもの           | 中身                                                                    |
| ---------------------- | ----------------------------------------------------------------------- |
| 表 2つ                 | `dk_companies`（契約会社）/ `dk_company_devices`（有効化したスマホ）    |
| サーバの小さな処理 2つ | `dk-issue-license`（ライセンス発行）/ `dk-register-company`（会社登録） |
| はんこ（署名鍵）       | Ed25519 の鍵ペア。**新しく作り直し**になる（後述）                      |
| ログイン設定           | メールのマジックリンク・戻り先URLの許可                                 |
| メール送信（SMTP）     | 差出人が「ダイコメ」になる                                              |

**今が一番安いタイミングです。**本番稼働している顧客データがまだゼロなので、引っ越しで失うものがありません。

## 準備済み（Claude 側・完了）

引っ越しを安全にするための下ごしらえは終わっています。

1. **接続先を1箇所にまとめた** → `js/dk-config.js`
   これまで接続先は **6ファイル 12箇所**に散らばっていました。1箇所でも直し忘れると
   「一部の画面だけ古い倉庫を読む」という一番たちの悪い壊れ方をします。
   今は **このファイルの2行を書き換えるだけで全部が新しい倉庫に向きます**。

2. **散らばりの再発を防ぐテスト** → `tests/unit/dk-config-single-source.test.js`
   誰かがうっかり別の場所に接続先を書いたら、テストが赤になって気づけます。（恒久ガード）

3. **サーバ処理のURL直書きをやめた**
   `DK_APP_BASE` という設定値で切り替わるようにしました（コードを触らずに本番ドメインへ移せる）。

4. **新しい倉庫を1回で作るSQL** → `supabase/migrate-standalone.sql`

5. **引っ越しが正しく終わったかを機械で判定する道具** → `scripts/verify-standalone-migration.js`

6. **はんこを安全に作り直す道具** → `scripts/gen-license-keypair.js`

## ★はんこ（署名鍵）は作り直しになります

ライセンスは「サーバがはんこを押す → アプリが照合表で確かめる」という仕組みです。

- **はんこ本体（秘密鍵）は、今の Supabase の中にしまわれていて、二度と取り出せません。**
  （安全のためにそういう作りになっています。ローカルの控えも削除済み。）
- なので新しい倉庫では、**新しいはんこを作ります**。
- 影響：**今テストで有効化してある端末のライセンスは無効になります**。
  → もう一度、会社URL（`?c=...`）を開けば有効化し直せます。本番の客はまだ居ないので実害ゼロです。

# ダイコメ距離精度アーキ ── 3者論戦 統合裁定報告書

司さんへ。推進派・現実派・判定官の3論証を突き合わせ、白紙書き直しの方針を1つに確定しました。先に言うと、3者は対立ではなく**完全収束**しました。「Google越え」の旗を降ろし、別の旗を立てる、という同一結論です。

---

## 1. 結論

**距離精度で「Google越え」は経営的に不可能(理論上のみ成立し、実機では証明不能 or 誤差以下)。3者全員が一致してこの結論。** センサー(武器A)は同一GPSチップ・同一MEMS依存ゆえ原理的にGoogleを超えられず、距離パイプラインへの純寄与はゼロ〜マイナス。データ(武器B)のうち3D標高距離は数学的に正しい方向の上乗せだが量が **+0.05〜0.3%** = JIS許容差±0.2%・DEM標高誤差±5m に埋もれ、課金距離の武器にならない。**唯一本物の武器は (B) の「道路属性snap精緻化(+約1pt 正答率)」と「完全オフライン全国データ保持」。** したがって honest Aクラス目標は次の一文に確定する:

> **「Google同等精度(対道なり ±3%以内・JIS合格圏)を、完全オフライン × 代行/防災特化 × トンネル/圏外でも継続、で全国どこでも安定して出す」**

「Google越え」は標榜しない。勝ち筋は**精度の軸ではなく可用性の軸**(Googleが構造的に提供できない「オフライン代行という戦場での同等精度」)。

---

## 2. 2武器の評価

### (A) センサー処遇表

GPS良好時の距離は純map-matching snapで既にGoogle級(実測9,436m vs Google 9,718m = 3%差、JIS合格圏中央)。**GPS良好局面でIMUが距離精度に足せるものは無い**(むしろband-aid層がバグ源 = 敵対的監査の指摘と一致)。

| センサー | 処遇 | 根拠(出典) |
|---|---|---|
| 加速度(variance静止判定) | **残す(静止局面のみ)** | creep加算防止に必須。Fix①で主信号化済。攻めでなく守りのゲート |
| ジャイロ/積分DR | **捨てる** | MEMSは加速度バイアスが位置に2次・ジャイロが3次累積([MDPI Sensors 2018, 18/5/1391])。商用系もGPS欠落7秒でDR停止([InertialSense FAQ])。スマホ実測 直線100秒で1km超drift([MDPI Sensors 2023, 23/17/7609]) |
| コンパス/磁気 | **捨てる** | 車載モーター/鉄のhard-iron biasでheading発散([PX4 magnetometer docs]) |
| Doppler速度 | **局面限定(静止判定の補助のみ)** | 精度0.1〜0.2m/s。GPSと同源で同時劣化、距離精度の主信号にできない |
| Kalman/融合 | **最小化(廃止寄り)** | 入力IMUが劣化すれば出力も劣化。snap+静止ゲートで代替可。過剰実装=バグ負債 |
| ZUPT | **静止検出としてのみ残す/foot-PDR流用は捨てる** | 車両は長時間停止型でgait周期型でない([Inertial Labs ZUPT]) |

**センサーの honest な役割 = 攻めのdead-reckoning破棄、守りの「静止判定+異常GPS棄却+復帰時snap再同期」に限定。** これが監査指摘の「band-aid層積」の根治。

決定打: 距離課金の最先進2社 Uber/Lyft が課金距離を **生GPS traceのHMM/Viterbi map-matching** で算出し、IMU dead-reckoning を課金主信号に**していない**([Uber CatchME/HMM]、[Lyft Engineering map-matching])。世界最大手が課金にIMU融合を採らないことが、過剰実装の何よりの証拠。

### (B) データ活用表

| データ | 距離精度 | UX/その他 | 白紙でどう使うか |
|---|---|---|---|
| **3D標高距離** | +0.05〜0.3%(=ノイズ) | 燃費/EV電費/防災高低 | **課金距離から除外。** Google越えの主武器に**しない** |
| **道路属性snap**(layer/oneway/lanes/maxspeed) | **+約1pt 正答率(本命)** | — | **Viterbi emission/transition costに正式投入。残す・強化** |
| POI | ほぼ無し | 目的地推定・住所② | 表示/入力補助に限定 |
| ハザード | 無し | 防災(冠水・通行止) | 代行/防災特化の差別化UXへ |
| 住所 | 無し | 住所②ライブ表示(既存) | 既存3段fallback維持 |

**3D標高距離をGoogle越えの主武器にするか → 明確にNO。** 理由を3者の数値で確定する:

- 3D増分は決定論的: 増分率 = √(1+g²)−1。勾配5%→**+0.125%**、8%→**+0.32%**、9%(日本標準最大)→**+0.405%**、12%(特例最大)→**+0.717%**([道路構造令解説 第16条]、[JIS D 5609:2019 距離許容差±0.2%])。
- この増分は**勾配区間だけ**に効く。代行1トリップの大半は平地(<3%→<0.045%)。トリップ加重で現実値 **+0.1〜0.3%**、全行程12%という物理的不可能条件でも上限+0.7%。
- **致命傷(判定官の決定打)**: 国土地理院 標高タイル z=14 = DEM10B(10mメッシュ)の鉛直精度は「**5m以内**」([GSI hyokochi/development])。3D信号(9.4kmで9〜28m)より**DEM由来ノイズ(±5m)が一桁大きい**。3Dを課金に入れるのは精度向上でなく**ノイズ注入**。
- 補足: 実測の対Google 3%差(ダイコメが少ない)の主因は3Dではなく**snap経路選定**。3Dは3%を埋める武器にならない。属性snapこそが正攻法。

**道路属性snapが本物の理由**: HMM/Viterbi map-matchingの誤マッチは並行道路・高架/地下・交差点に集中([PLOS One 2019, pone.0216476])。属性をstates/emissionに組むと正答率が **並行道路95.9→98.3%、平均約+1.2pt**([PLOS One PMC11078395]、[arXiv 2505.05007]、[Wiley 2021 2nd-order HMM])。**Googleは課金アプリに2D道なり距離しか返さない**が、ダイコメは端末内属性bitmapで誤snap局面を潰せる = 「同等を全局面で確実に達成する保険」。

## 3. 「Google越え」を狙う局面 / 狙わない判断

**狙わない(距離の小数点軍拡を放棄):**
- IMU dead-reckoning による精度向上 → 同チップ依存で原理的に不可。**距離パイプラインから撤退。**
- 3D標高による課金距離上乗せ → 量が許容差・DEM誤差以下。**距離計算から除外。**

**狙う = ただし「精度越え」でなく「可用性で同等を再現」:**
- **トンネル/圏外/オフライン局面**: Google Directionsは機能しない。ダイコメは端末内に道路topology保持 → GPS復帰後の経路補間でtopology既知。**IMU積分で埋めるのでなく、道路topology補間+復帰時snap再同期**で対処。
- **並行道/高架地下の誤snap局面**: 属性付きViterbiでGoogle同等以上の道路選定。

**完全オフラインのスマホで実装可能な範囲**: 属性付きViterbi snap(geometry+layer/oneway/typeCodeはroads-v7内包済)、静止判定、topology補間 ── すべて端末内完結で実装可能。3D/incline計算も技術的には可能だが**やらない**(ノイズ源)。

## 4. 白紙アーキ(pipeline.js単一state machine + map-matcher中核再利用 + roads-decoder活用)への変更

1. **map-matcher中核を距離精度の主役に据える**。Viterbi emission/transition cost に **layer(高架地下)/oneway/typeCode** を正式投入。roads-decoderはこの属性供給に最適化。
2. **3D/inclineは distance_m 計算に組み込まない。** → **distance_m の定義は 2D 道なりsnap累積のまま不変**(2D→3Dへの変更は行わない)。これにより calcFare料金式・課金距離=道なりsnap累積・タクシー方式全加算は**完全に不可侵を維持**。3Dは将来の表示/燃費/防災レイヤーへ温存(課金回路と非共有)。
3. **センサー融合層を clean fusion へ縮約**: pipeline.js の single state machine 内で、加速度variance静止判定 + ZUPT流静止ゲート + 異常GPS棄却 のみを保持。**ジャイロ積分DR/コンパス/Kalman融合ブロックは削除**(band-aid層積の解体 = 保守コスト激減・バグ源除去)。
4. **GPS劣化局面の処理を「IMU積分」から「topology補間+snap再同期」へ差し替え**。warmup 47県非同期fallback問題は、距離主役がsnapなら属性は遅延ロード許容(初期geometryのみでsnap可)で緩和。
5. **distance_m 定義は変えないため calcFare への影響はゼロ**。これは絶対ルール(distance_m不可侵・GPS直線距離禁止・業務vs trip完全分離)と全整合。

## 5. 元の野望と現実 ── 率直な総括と1つの方針

元の野望は「センサー融合と3Dデータで距離精度Google越え」でした。3者が独立に証拠で検証した結果、**野望の前提が崩れています**:

- 純map-matching snap は**既にGoogle級**(3%差・JIS合格圏中央)。出発点が既に高い。
- 伸び代と期待した**3Dは +0.3%上限・DEM±5mノイズ以下**で測定不能。
- 伸び代と期待した**センサーは同チップ依存でゼロ〜マイナス寄与**、しかもバグ負債の主因。
- 唯一の本物の伸び代は**属性snap(+1pt)**と、精度でなく**可用性の Google越え(オフライン)**。

率直に言えば「Google越え」は看板倒れになる(標榜は捏造に近い)。しかし**負けでは全くない**。Googleが構造的に立てない戦場 ── 完全オフライン・トンネル・圏外・代行/防災特化 ── で同等精度を全局面安定供給することが、業界トップの正体です。

**確定する白紙方針(これ1つで進めてください):**

> **honest Aクラス = 「Google同等精度(±3%・JIS合格圏)× 完全オフライン × 代行/防災特化 × 必要なデータだけ」。**
> 距離精度の主役 = 属性付き2D Viterbi snap(distance_m 定義は2Dのまま不変)。センサーは静止判定+異常棄却+復帰再同期の守りに限定(攻めのDR・コンパス・Kalman廃止)。3Dは課金から除外し将来の表示/防災へ温存。勝ち軸は精度越えでなくオフライン可用性。calcFare式・道なりsnap累積・完全オフライン・業務/trip分離は全て不可侵のまま整合。
